# Read-only live verification harness

`live-verify.mjs` is prepared for use after an authorized Studionet deployment and wallet-approved lifecycle transactions. It performs reads and finality polling only; it never signs or sends transactions. The filled config must identify a new test contract and cannot use the historical production address. Before reading code or state, it calls `eth_chainId` on its fixed RPC and refuses any result other than Studionet `61999`.

It verifies finalized deployed source bytes against SHA-256 `cac38f9d2a607446b071aecfe7e00ed0be96c2b31dd4ea9f9633477295e1b45e`, reads canonical state with the pinned SDK's `TransactionHashVariant.LATEST_FINAL`, and reads source through Studio's address-only `gen_getContractCode` RPC after deployment finality is established. It checks supplied transaction finality/execution and binds each deployment, publish, submission and assessment hash to the candidate contract, application wallet, decoded method and canonical arguments. It also asserts each fixture's exact repository, full commit SHA, applicant wallet, program ID, fresh nonce, marker hash, every file fingerprint, outcome, provenance, issue code and criterion vector.

The template is intentionally incomplete and cannot pass. The filled run record for the authorized 2026-10-16 test is `live-run.2026-10-16.json`; the complete canonical capture is `live-evidence.2026-10-16.json`. A successful run requires exactly five named lifecycle assertions: `positive`, `negative`, `corrected-r1`, `corrected-r2`, and `unavailable-evidence`. It requires that only `corrected-r1` is superseded, that corrected revisions share an entry and applicant but use distinct commits, that the canonical qualified roster contains the unique positive/corrected-r2 entry, and that a finalized failed unauthorized action leaves a captured entry state unchanged.

The harness has syntax and offline regression validation against the repository's pinned `genlayer-js@1.1.8` types/runtime. It was run against the existing deployed remediation contract and all captured lifecycle transactions. The run reached finality and canonical readback, then stopped at the positive review's missing marker fingerprint because every live evaluator snapshot was `PROVIDER_UNAVAILABLE / REPOSITORY_UNAVAILABLE`. A cooldown-authorized retry (`a6`) reproduced the same result, so the harness correctly refused to claim any `QUALIFIED` or `NOT_ESTABLISHED` lifecycle.

The qualified-roster check deduplicates a corrected revision that shares its entry with the positive case. This is required by the contract's append-once roster semantics and is covered by the release-prep regression test.
